# 基幹システム Web 版（Access からの移行）

Access で作った基幹システム 8 つ（受注登録・丸北WorkStation・倉庫管理System・製造管理 丸北・製造計画・包装場管理System・WEB連携・手配出力用カレンダー）を、クラウドで動く Web アプリに移すためのフォルダ。

- 調査と計画：[../docs/access移行/](../docs/access移行/00_全体像.md)
- 進め方：[移行計画](../docs/access移行/10_移行計画（案）.md)

## フォルダ

| フォルダ | 中身 |
|---|---|
| `migrate/` | Access のデータを PostgreSQL に移す道具 |

## データの移し替え（migrate）

1. Access のファイルを `migrate/data/` に置く（ファイル名は `migrate/sources.json` のとおり）。このフォルダはリポジトリに入れない。
2. PostgreSQL を用意し、次を実行する。

```
cd kikan/migrate
PGURL=postgresql://ユーザー@ホスト/データベース python3 accdb_to_pg.py sources.json
```

- Access ファイル 1 つが、PostgreSQL のスキーマ 1 つになる（例：丸北WorkStation.accdb → `ws`）。
- 表と項目の名前は Access と同じ（`ws."TD_出荷"."輸送ID"` のように二重引用符で囲んで使う）。
- 何度でもやり直せる（実行のたびに、そのスキーマを作り直す）。
- 結果は `移し替え結果.md` に出る（表ごとに Access の件数と移した件数を比べる）。
- 必要なもの：mdbtools（`mdb-tables`・`mdb-schema`・`mdb-export`）、psql、Python 3。
- 個人の住所録（`TM_専務専用住所録`）は移さない（`accdb_to_pg.py`・`csv_to_pg.py` で飛ばす）。

## 書き出した CSV からの取り込み（csv_to_pg）

Access の画面側ファイルで `ExportTables`（表を CSV と fields.txt に書き出すプログラム）を動かして作ったフォルダを取り込む。

```
cd kikan/migrate
PGURL=... python3 csv_to_pg.py --fe 受注登録FE --dir 書き出したフォルダ
```

- fields.txt の型で表を作り、同じ名前の CSV を入れる。
- リンクしている表は、本来の持ち主のスキーマに入れる（例：受注登録FE の「TD_出庫」→ `soko."TD_出荷"`）。対応は `links/画面側ファイル名.json`（画面側ファイルの中の情報から作ったもの）。
- 画面側ファイルの中の表は、`sources.json` でその画面側ファイルに割り当てたスキーマ（例：`juchu_fe`）に入れる。
- ほかのシステムの表がいっしょに書き出されていて、すでに取り込んだものを上書きしたくないときは `--skip-schemas ws,soko` のように指定する。

## 商品マスタ・得意先マスタを 1 つにまとめる（unify_masters.sql）

Access では画面側ファイルごとに商品マスタ・得意先マスタの写しがあり、中身が少しずつ違う（WorkStation の写しは古い）。
Web 版では `kyotsu."TM_商品マスタ"`・`kyotsu."TM_得意先マスタ"` の 1 つにまとめ、各スキーマ（juchu_fe・ws_fe・soko_fe・seizo_fe・housou_fe・tehai_fe・web_fe・keikaku）の同じ名前のところはビューにする。

```
psql "$PGURL" -v ON_ERROR_STOP=1 -f unify_masters.sql
```

- 中身はいちばん新しい写し（受注登録など 6 つ）を使い、そこで消された古い商品は製造計画・WorkStation の写しから足す（過去の受注・出荷の商品名を出すため）。
- 「ロボットプログラムNo」は製造計画（なければ WorkStation）の値を入れる。
- 取り込みをやり直したあとにもう一度流す。もとの写しは `old_master` スキーマに取っておく。

## パソコンごとにあった表を空にする（reset_per_pc.sql）

Access で各パソコンの画面側ファイルにあり、人ごとに中身が違っていた表（保存した出荷抽出・輸送抽出の条件、パレット配置図、出荷停止の確認の印）は、Web 版では全員が同じものを使う。本番に移すときは空から始める（2026/10/23 利用者）。取り込みのあとに流す。

```
psql "$PGURL" -v ON_ERROR_STOP=1 -f reset_per_pc.sql
```

## Excel で保存した CSV からの取り込み（excel_csv_to_pg）

Access の表を Excel に貼り付けて CSV にしたもの（型の情報がないもの）は、同じ形の表の型を借りて入れる。

```
PGURL=... python3 excel_csv_to_pg.py --csv 倉庫管理の受注.csv --table soko.TD_受注 --like juchu.TD_受注
PGURL=... python3 excel_csv_to_pg.py --csv 転売品管理の受注.csv --table tenbai.TD_受注 --like juchu.TD_受注
PGURL=... python3 excel_csv_to_pg.py --csv 原料管理の出荷.csv --table genryo.TD_出荷 --like soko.TD_出荷
```

- 日付（13-Oct-26 など）・TRUE/FALSE・カンマや ¥ の付いた数字を読み替える。入れる前に表を作り直す。
- `--like` の表にない項目は、入っている値から型を決める（真偽・日時・数・文字）。全部空欄の項目は文字になる。

## Web アプリ（app）

| フォルダ | 中身 |
|---|---|
| `app/server/` | サーバー（Fastify・PostgreSQL）。ログイン、受注の API |
| `app/client/` | 画面（React）。Access の画面に近い見た目にしている |

```
cd kikan/app
npm install
npm run build                      # 画面を作る（dist/）
PGURL=... npm run create-user -- ログインID 名前 パスワード [admin]
PGURL=... npm start                # http://localhost:3000 で開く
```

- 表は Access と同じ名前のものを使う（例：`juchu."TD_受注"`）。Web 版だけで使う表（利用者・ログイン・設定）は `app` スキーマに置く（`server/schema.sql`）。
- 開発中は `npm run dev`（画面は http://localhost:5173）。
- 受注の削除には、Access と同じく合言葉が要る。合言葉はプログラムに書かず、サーバーを動かすときに `JUCHU_DELETE_PASSWORD` で渡す（今の Access と同じものにする。2026/10/20 確認）。渡していないときは削除できない。

### 見本版（Artifacts で試すもの）

サーバーとデータベースがなくても画面を触れるように、ブラウザの中だけで動く見本版を作れる（`client/src/demo/`）。

- データベースは PGlite（ブラウザの中で動く PostgreSQL）。表の形は本番と同じ（`schema.sql`、pg_dump の表の定義だけ）。
- サーバーの処理は本番と同じものを使い、データベースの接続（`db.ts`）とログイン（`auth.ts`）だけ差し替える（`vite.demo.config.ts`）。
- データはすべて作り物（`make_data.py` で `data.sql` を作る）。区分などの一覧表だけ、取引先名の入らないものを写す。日付は開いた日が基準。
- Artifacts の画面では確かめる窓（confirm など）が出ないので、見本版では知らせを右下に出し、確かめる窓は OK、合言葉は demo で進める。直した内容はページを閉じると消える。
- 作り方：`npm run build:demo` → `dist-demo/artifact.html` と `dist-demo/assets/` を Artifacts に置く。表の形を変えたら `schema.sql` を作り直す（`pg_dump --schema-only -N bk -N old_master` から `\restrict` 行と `set_config` 行を除く）。

### 画面の決まり（全部の画面で同じにする）
- **日付**の欄は、ダブルクリックで共通のカレンダー（Access の FSD_日付選択）が出る。祝日・第 2/第 4 土曜などの休み・会社の特休（TM_イベントスケジュール）は赤の下線、日曜は赤、土曜は青、今日は黄色。
- 共通コードには**運送会社**（`kyotsu="unso"`、FSD_運送会社選択）もある。
- **共通コード**（全システムで使うマスタのコード：得意先の短縮コード＝受注先・届け先・帳合先・入庫名義・取引先など、商品コード）が入る欄は、色を変える（うすいオレンジ）。ダブルクリックで、そのマスタ（得意先・商品）を名前から探す画面が出て、選ぶとコードが入る。
- 作り方：入力欄の部品（`client/src/formParts.tsx` の `Field`・`Combo`）に `kyotsu="tokui"`（得意先）か `kyotsu="shohin"`（商品）を付ける。これから作る画面も同じようにする（2026/10/21 利用者の依頼）。
- 相手先のコード（日本食研・SB などの側のコード）は共通コードではないので、この印を付けない。
- 探す画面は Access の FSD_得意先選択・FSD_商品名選択 と同じつくり：カナのボタン（全・ｱ行〜ﾜ行・1 文字ずつ）、文字（商品は探す項目を選べる）、商品は分類・原料・旧コード、得意先は地区・都道府県・グループ・保管で絞る。見出しを押すとその順に並ぶ。行をダブルクリック（または選んで［選択］）で決める。得意先は短縮コードでも探せる。

- 処理中の表示（2026/10/22 利用者の依頼）：サーバーへの問い合わせが 0.3 秒より長くかかったら、画面の真ん中に「処理しています…」を出す（`client/src/api.ts`。全部の画面で共通。ファイルの読み込み・Excel の書き出しも同じ）。出ている間は画面を押せない（二度押しを防ぐ）。

### 速さについて
- Access から移した表には探すための索引（インデックス）がなかったので、よく使う項目（出荷の 出庫ID・輸送ID・在庫ID・受注ID・入庫ID・出荷日、在庫の 在庫ID・入庫ID、便の 輸送ID、入庫ID、受注ID など）に付けた（`server/schema.sql`。サーバーを起動すると付く）。古いデータを消す画面の件数計算が 6.7 秒 → 0.04 秒になった。
- 今の画面は、ほとんど 0.1 秒以内（実データ）。日別の在庫の作り直し（2 年分ほど）が 2 秒ほど。
- 計算はサーバーの JavaScript（実行時に機械語に直して動く）とデータベースで行う。遅いときは、まず索引と「1 行ずつ問い合わせる」書き方を直す。それでも足りないところだけ、もっと低い水準の言語（Rust など）を考える。
- これから作るもので時間がかかりそうなもの（2026/10/22 利用者）：丸北WorkStation の架空在庫計算、倉庫管理の保管賃計算。作るときに実データで時間を測り、必要なら作り方を工夫する。
