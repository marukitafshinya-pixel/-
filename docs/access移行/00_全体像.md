## 2. データの流れ（いまわかっている主なもの）

```
受注登録 ──受注（写し）──▶ 丸北WorkStation ──残数・手配状態──▶ 受注登録
                                 ▲   │
製造計画 ──生産計画・変更案内──────┘   │
製造管理 ──入庫（出来高）─────────▶  │──在庫の数を直接書き換え──▶ 製造管理
倉庫管理 ──出庫・名義変更──────────▶ │
転売品・原料 ──出荷──────────────▶ │──輸送ID・出庫IDを書き戻し──▶ 転売品・原料
                                     └──検査結果──▶ 仕掛原料管理
販売管理（販盛）◀──ブラウザ自動操作──▶ 受注登録
```

## 3. どのシステムにも共通する点

- **同じデータの写しがあちこちにある**：受注は 4 か所、商品マスタは 8 か所、得意先マスタは 6 か所。写しをそろえるのはプログラムか手作業。
- **得意先の「短縮コード」がすべての共通の番号**（倉庫・届け先・名義・取引先・運送会社）。
- **マスタや設定が画面側ファイルの中にある**ので、PC ごとに中身が違うおそれがある。
- **ログイン・権限がない**。編集は固定パスワード。
- **ID の直接書き込みが多い**：629 大阪丸北、1 丸北北海道、11 丸北北海道（工場）、150 JAふらの、191 ふらのソテー工場、360 日本食研、1237 和弘食品 など。
- **Excel のひな形への書き込み、PC ごとの OneDrive の場所、共有フォルダのパス** に頼っている。
- **エラーが出ても止まらない書き方** が多く、不具合が表に出ていない。
- 受注登録・WorkStation の両方で、**データを全部消してしまうおそれのある命令** が見つかっている。

## 4. Web 版の考え方（案）

1. **データベースを 1 つにまとめる**：写しをなくし、受注・出荷・在庫・マスタを 1 か所で持つ。システムごとの画面は「同じデータを見る別の画面」にする（SOA の分け方は画面・機能の単位として残す）。
2. **共通の番号（短縮コード）はそのまま使う**：今のデータをそのまま移せる。
3. **直接書いてある ID は設定（マスタ）に移す**。
4. **在庫は入出庫の記録から計算する**（残数を足し引きで持たない）。
5. **帳票は PDF／Excel をサーバーで作る**。
6. **ログインと権限**を入れる。
7. **段階的に移す**：しばらく Access と並行で動かすなら、Web と Access の間でデータを行き来させるしくみが要る。全部まとめて切り替えるか、システムごとに順に切り替えるかを決める。

## 5. 決めていただきたいこと

1. 置き場所：社内サーバーか、クラウドか。外から使う必要があるか。同時に使う人数。
2. 切り替え方：全部まとめて切り替えるか、システムごとに順に切り替えるか。
3. 不具合：今の動きのうち不具合は直してよいか（おすすめは「直す」）。
4. 動いていない機能・古い画面：作り直すか、やめるか（各報告書の 4 章）。
5. マスタの正本：どのシステムのマスタを正とするか。
6. 販売管理（販盛）との連携：ブラウザ自動操作を続けるか、CSV のアップロードにするか。
